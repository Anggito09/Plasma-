1. Ringkasan eksekutif

Temancipta adalah aplikasi web untuk kafe dan usaha makanan-minuman skala UMKM. Satu instalasi = satu kafe = satu basis data terpisah. Petugas tidak mengunduh aplikasi: kasir, dapur, TV antrean, riwayat, dan keuangan dibuka dari peramban.

Inti produk bukan hanya mencatat uang masuk. Inti produk adalah mengukur pelayanan dari pesan sampai siap, lalu memberi owner angka dan saran yang bisa dieksekusi: menu mana yang lambat, jam berapa dapur kewalahan, hari mana target terlewati, petugas mana yang cepat, menu mana yang tidak laku.

Janji yang boleh disampaikan ke klien: nomor antrean unik per hari (reset 00.01 zona kafe), struk menyimpan harga saat transaksi, dapur tidak bisa “saling timpa” status, TV memanggil dengan suara, keuangan masuk−keluar, analisa AI berangka (bukan opini kosong), PBJT terpisah dari PPN.

2. Tujuan bisnis & ruang lingkup (BRD)

2.1 Masalah yang diselesaikan

  • Antrean kertas/nomor manual dobel saat ramai.
  • Dapur dan kasir tidak melihat status yang sama.
  • Owner tidak tahu apakah pelayanan 10 menit tercapai, atau hanya “rasanya lama”.
  • Menu mati dan menu lambat baru ketahuan setelah stok busuk / komplain.
  • Laporan keuangan tercecer di buku dan chat.

2.2 Tujuan terukur

2.4 Asumsi

  • Perangkat terhubung internet. Tidak ada mode offline menulis pesanan.
  • Pembayaran tunai/QRIS/transfer dilakukan di luar gateway; sistem hanya mencatat metode.
  • Printer struk memakai cetak peramban (profil kertas 80 mm).
  • Suara TV memakai mesin suara peramban (Chrome disarankan).
  • Zona waktu dikunci saat setup (WIB / WITA / WIT).

4. Alur kerja operasional (workflow)

4.1 Buka shift

  1. Kasir masuk di perangkat kasir.
  2. Dapur masuk di perangkat dapur (/dapur).
  3. TV masuk akun display, aktifkan suara sekali, layar penuh.
  4. Pastikan indikator Live. Jika “Menyambung…”, jangan terima pesanan baru.

4.2 Siklus satu pesanan

Pelanggan pesan → Kasir pilih menu (qty, catatan, dine-in/takeaway) → Isi nama panggilan → Diskon (Rp) opsional → Sistem hitung: subtotal − diskon + service% + PBJT% → Kasir terima uang di luar sistem, pilih metode (Tunai / QRIS / Bank) → Simpan → server beri nomor A0001, A0002, … (unik hari itu) → Struk: snapshot nama+harga saat itu (ubah menu nanti tidak mengubah struk lama) → Dapur: Menunggu → Proses → Siap & panggil → TV: ucapan “Nomor antrean A … [nama]. Silakan ambil di konter.” → Kasir/dapur: Diambil → status Selesai (hilang dari papan, tetap di riwayat) → Batal hanya waiting/preparing/ready + alasan wajib; refund di luar sistem

4.3 Status pesanan

StatusArtiAksi berikutnyaCap waktu
waitingBaru masuk dapurProsescreated_at
preparingSedang dibuatSiap & panggilprepared_at (pertama kali)
readySiap diambil, TV memanggilUlangi / Diambilready_at
completedSudah diambil—completed_at
cancelledDibatalkan—cancel_reason

Pindah status memakai versi (optimistic lock): dua petugas tidak bisa menekan tombol yang sama dan menghasilkan dua panggilan. Panggilan TV memakai ID permintaan unik (boleh diulang tanpa dobel event).

4.4 Nomor harian

  • Format tampilan: A0001 … A1000 … (lebar minimal 4 digit, tidak dibatasi 9999).
  • Reset otomatis pada pergantian hari bisnis zona kafe (bukan jam HP).
  • Pesanan kemarin yang belum selesai tetap tampil di dapur/TV, dengan label tanggal agar tidak dikira nomor hari ini.

4.5 Evaluasi owner (setelah ramai / tutup toko)

  1. Riwayat hari itu: KPI pesanan, omzet, batal, rata siap, rata ambil, % target.
  2. Jam ramai: kolom jam 08.00, 09.00, … jam tersibuk ditandai; merah = lewat target.
  3. 10 terlambat + kecepatan per petugas + tunggu per pelanggan.
  4. Keuangan: rentang tanggal, grafik batang/donat/tren, catat pengeluaran, laba, CSV.
  5. Analisa AI: 5 seksi wajib (tren, menu, kecepatan vs target, bayar, 3 saran). Jika AI gagal, aturan tetap menulis 5 baris yang sama strukturnya.

7. Non-fungsional

7.1 Keamanan

  • Sandi: PBKDF2-SHA256, 100.000 iterasi, garam acak per akun.
  • Token sesi: dua UUID acak; yang disimpan hanya hash SHA-256.
  • SQL berparameter. Teks pelanggan dirender lewat React (bukan HTML mentah).
  • Header API: no-store, nosniff, DENY iframe, referrer same-origin, matikan kamera/mikrofon/lokasi.
  • Login dummy hash jika username tidak ada (anti enumerasi waktu).

7.2 Keandalan

  • Papan kasir/dapur poll 3 detik; event TV 5 detik (hemat kuota, panggilan tetap berurutan).
  • Klien mengulang otomatis 2× jika jaringan putus atau server 5xx (kecuali login/setup).
  • Tidak ada antrian tulis offline. Data hidup di server, bukan localStorage.
  • Backup: skrip npm run backup mengekspor D1; klien bayar wajib jadwal harian.

7.3 Pajak (informasi produk, bukan nasihat hukum)

Menurut DJP / UU HKPD: makanan-minuman yang disajikan restoran/kafe (ada meja/kursi/peralatan) adalah objek PBJT daerah, tarif maksimal 10%, bukan PPN. UMKM di bawah ambang Perda setempat bisa tidak wajib pungut — isi 0. Service charge adalah kebijakan kafe, bukan pajak. Owner menyesuaikan Pengaturan → Kafe.

7.4 Performa yang diuji

Paket uji otomatis (Node + SQLite kompatibel D1) mencakup zona waktu Indonesia, 1.250 nomor unik, lewat tengah malam, idempotensi, mesin status, peran, throttle login, insights tanpa nama pelanggan, PBJT/diskon. Ini uji kebenaran logika, bukan SLA latensi produksi.

8. Di luar versi ini

Jangan dijanjikan di proposal kecuali ada kontrak pengembangan terpisah:

  • Stok bahan / resep / HPP otomatis
  • Nomor meja, split bill, void edit item setelah tersimpan
  • Gateway pembayaran (midtrans dll.) — QRIS hanya gambar + catatan metode
  • Printer ESC/POS native (yang ada: cetak peramban 80 mm)
  • Aplikasi Android/iOS toko; mode offline kasir
  • Loyalty, member, voucher berjangka
  • Multi-cabang satu login (modelnya: 1 kafe = 1 instalasi)
  • Upload foto ke server kami (sekarang URL https)
  • Reset sandi staf lewat email; 2FA pengguna akhir (2FA yang wajib: akun Cloudflare penyedia)

Peramban (Kasir / Dapur / TV / Owner) │ HTTPS same-origin /api/... ▼ Cloudflare Worker ← Workers AI (Llama, opsional) │ ▼ Cloudflare D1 (SQLite) — satu database per kafe │ ▼ Migrasi Drizzle 0000 … 0005

Rumus uang

subtotal = Σ price × quantity diskon = 0 … subtotal (input kasir) service = round((subtotal − diskon) × service_pct / 100) PBJT = round((subtotal − diskon + service) × tax_pct / 100) total = subtotal − diskon + service + PBJT

Rumus SLA

wait = ready_at − created_at (hanya jika ready_at ≥ created_at) pesanan makanan jika salah satu item.id ada di produk kategori makan|roti|kue|snack|food|bakery|cake|pastry|dessert target = target_food_min jika makanan, else target_drink_min on_target jika wait ≤ target × 60.000 ms

12. Uji penerimaan klien (UAT)

  1. Masuk admin, kasir, dapur, TV — masing-masing hanya melihat menunya.
  2. Buat pesanan, catat nomor. Refresh kasir, pesan yang sama tidak membuat nomor baru.
  3. Ubah harga menu, struk lama tidak berubah.
  4. Dua perangkat dapur tekan “Siap” bersamaan: hanya satu yang menang, satu panggilan TV.
  5. TV menyebut nomor dan nama.
  6. Tunggu > target makanan: kartu dapur merah.
  7. Isi PBJT 10% + diskon: rincian kasir dan struk sama dengan kalkulator.
  8. Keuangan 7 hari: grafik tidak “melebar tak terbaca”; analisa 5 nomor; tidak ada nama pelanggan di narasi.
  9. CSV riwayat terbuka di Excel.
  10. Nonaktifkan kasir: HP kasir langsung tidak bisa /api/me.
